# The monitor's UI and plugins

What each panel, tab and plugin of the monitor does. To install and start the monitor, see the
[README](../../README.md); for the phone page, [phone_manual.md](phone_manual.md).

## Panels

Some plugins show content in panels separate from the main control panel. Panels can be moved, docked, collapsed and resized:

- Drag the bar at the top of a panel to float it, or drop it on a screen edge or next to another docked panel to dock it.
- The control at the right end of that bar collapses and expands the panel.
- Drag the edge of a floating panel to resize it.

Where they start:

- The main panel (Stop all, health) floats in the top left corner.
- The console, minimized, in the bottom right, and the **Plan plots** and **Exec plots** windows (`assembly_steps`,
  `movement_exec`), minimized to their bars, at the bottom, right of the main panel; each opens by itself when it has
  something new to show.
- The plugins' tabs are docked on the right, in the order the plugins start: **Assembly** (below), **Collisions**,
  **Control** (`robot_control`, a tab per robot), **Plan** with a tab per planner panel (**Base**, **Motion**,
  **Arm**), **Mocap** with **Bars** and **Streams**, and a tab per other plugin; each plugin's tabs carry its icon. Drag a tab out to give it a window of its
  own, or into another panel.
- Tools and plots not needed every session (`obstacles`, `debug_gizmo`, `mocap_probe`, the calibration plots) start in
  a minimized strip at the right edge, nested under their plugin's name.
- Some plugins keep extra views in folders at the bottom of their tab, closed at start: `mocap_probe` shows the probe
  state big enough to read from a distance in a **Status** tab inside the **Big status** folder; `base_exp` shows its
  live error and command plots in an **Errors and commands** tab inside the **Live plots** folder.

In the browser's 3D view, left-drag rotates, right-drag pans, scroll zooms.

### Your own layout

Dragged windows are not remembered (viser never reports them). To keep a layout, save it as
`~/.config/husky_monitor/layout.json` on the laptop running the monitor (`mkdir -p ~/.config/husky_monitor` first), or
name another file with `layout:=<path>`. It is yours, never in git; without it the monitor uses the layout above.

It can give a top-level folder a window of its own, move a plugin's tab or start it hidden, place a window a plugin
made itself, by its title, and set preferences: the monitor's `ghost_timeout` under `preferences`, and each plugin's
own under `plugins.<name>.preferences` (`console`: `hidden`, the sources hidden at start; `assembly_run`:
`big_buttons`, big buttons in the Assembly tab); the monitor logs each entry it cannot use and skips it. The format is
in `ui/layout.py`.

Example, YH's layout: the Plan tabs in a floating window right of the main panel; the two plot windows minimized side
by side at the bottom left (a negative coordinate counts from the right or bottom); the console's ticks and runtime
lines hidden; big buttons in the Assembly tab; ghosts kept until another plugin shows its own (`0`):

```json
{
  "windows": {"Plan": {"float": [410, 15], "width": 420}},
  "plugins": {
    "console": {"preferences": {"hidden": ["ticks", "runtime"]}},
    "assembly_run": {"preferences": {"big_buttons": true}}
  },
  "panels": {
    "Plan plots": {"float": [15, -15], "width": 460, "height": 560, "minimized": true},
    "Exec plots": {"float": [485, -15], "width": 460, "height": 560, "minimized": true}
  },
  "preferences": {"ghost_timeout": 0}
}
```

### For plugin authors

Plugins add tabs with `ctx.view.ui()` and `ctx.view.tab()`, and plugins with the same tab path
share it through bands, `ctx.view.ui(band=...)` (`plugins/__init__.py`). To pick a plugin's icon,
`scripts/icon_gallery.py` shows every icon viser ships, searchable (tabler.io shows newer versions that can look
different).

## The Assembly tab

The **Assembly** tab holds `process`, `assembly_steps`, `movement_exec` and `assembly_run`; it is where you pick and
run the current step, top to bottom:

1. the process section (Folder, Load, its two boxes);
2. the run (its chips, Continue newest / Continue match / New run, where each robot is);
3. the action list and its ▲ / ▼, the step slider, the boxes for what the 3D view draws, the movement's details;
4. the step's chips and lines;
5. **Live IK**; **Check tool0**; **Plan**; Play / Clear; the **Preview time** and **Motion time** sliders;
6. **Exec**; the prompt with **Confirm** | **Cancel**;
7. **Mark done** | **Reopen**;
8. the settings (Ignore built bars, Visual diagnosis, Insert split mm, Spiral, Spiral s, Spiral turns, Servo by bar,
   Retreat live axis, Retreat compliant, Dry run);
9. the folded **Advanced planning**.

The **Plan plots** and **Exec plots** windows float at the bottom left.

The action list shows each action's mark from the run (`· pending`; `· done`, green; `· done (assumed)`, orange; the
selected action blue), and the movement you pick there (a row, the step slider, ◀ mv / mv ▶, a movement button)
becomes the run's current step, except while `movement_exec` has a robot's lease for a step.

Buttons are coloured by what they do: teal computes without moving (Live IK, Plan), blue starts a motion (Exec; while
other robots are not measured it turns amber, reads **Exec?** and asks for a second press within 5 s), green lets a waiting step go on
(Confirm), red stops (Cancel), yellow records (Mark done).

## Phone

A phone page for walking next to the robots: open `http://<laptop's 192.168.0.x address>:8081` on a phone on the robot
WiFi, held upright. It has **Stop all**, the health banner, and a tab per plugin: **Control** (D-pad, gripper
Open/Close/Stop, Free drive while held), **Health**, **Streams**, **Mocap**, **Calibration** and **Exec** (Confirm and Cancel for `movement_exec`).
Setup, every button and troubleshooting: [phone_manual.md](phone_manual.md). Plugins add a tab with `ctx.view.phone()`
(`plugins/__init__.py`).

## Clearance

Every button that moves a robot from the monitor keeps it clear of everything in the scene while it moves: the other
robots, the obstacles, the bars and the robot itself. Once the robot comes closer than the move's **clearance**, the
monitor soft stops it (Resume in Health) and the button's chip says what it came too close to; the **Collisions** tab
shows the hit. It is checked a tick or two behind the robot, from mocap and the joint states: it is no emergency stop,
keep the e-stop at hand.

How close it may come depends on the kind of move. Planned moves keep more than that from everything, so a robot that
follows its plan a little off does not trip it:

| Move | Its plan keeps | It soft stops within |
|---|---|---|
| An arm along a plan: the arm planner's **Commit**, calibration's **Go** (moves and sweeps) | 1 cm | 5 mm |
| An arm by hand: robot_control's joint and tool0 jogs, calibration's tool pad | (no plan) | 5 mm |
| A base along a plan: the base planner's **Commit**, base_exp's **Start** | 10 cm (the **Margin**) | 5 cm |
| A base by hand: every D-pad (robot_control, calibration, phone) | (no plan) | 5 cm |
| Assembly **Exec**, a plain motion along its plan | contact only | contact |

- **A plan that keeps less.** Arm and base plans follow one rule: everything keeps the usual distance (1 cm for an
  arm, the **Margin** for a base), and only what the start or target is already closer to keeps as much as it has
  there (the plan's line names it: "keeps only 0.3 cm between right_ur_arm_wrist_1_link and the right_ur_arm tool",
  "keeps only 3.5 cm from bars/B25"). A base plan also keeps the **Margin** you set, which you may lower below 10 cm to
  get through a tight spot. Then the clearance is half of the least the plan keeps (0.15 cm, or 4 cm for an 8 cm
  Margin), and an amber **small clearance** chip says so before you commit (calibration says it in Go's prompt). The
  assembly planner checks contact only,
  so Exec's clearance trips on contact only, with the same chip.
- **A start already too close is refused.** Nothing is sent and a red **starts too close** chip (robot_control greys
  its buttons) says what is in the way. Before the press, the chip already shows while the robot stands that close.
- **The Clearance box**, below each set of buttons, ticked at start. Untick it to move out of a tight spot: the buttons
  turn amber and nothing soft stops the robot. One box covers a robot's buttons on the laptop and the phone alike.
  base_exp has none: its runs always keep their clearance.
- **Other robots not measured** (mocap lost, no joint states) are checked as stand-ins where they were last seen. An
  arm's Commit or Go takes a robot whose only unknown parts are arms out of the moving arm's reach without asking; any
  other makes the button ask for a second press. A base drive always asks (its Commit and Start): driving changes the
  distance to every robot, however far. The D-pads and jogs never ask; the amber chip naming the robots not measured
  is the warning.
- **No clearance**: free drive (the arm is in your hand), Exec with **Ignore built bars** ticked (the plan may pass
  through them; an amber **no clearance** chip says so), and Exec's inserts, retreats, Robotiq handoffs and servo
  passes, which touch the bars by design.

Stopping in time at speed is not covered: the base rolls about 10 cm after a trip at 0.2 m/s. Drive slowly near
things. For plugin authors: `ctx.clearance` and the kinds of move (`ARM_MOVE`, `BASE_DRIVE`) in
`world/clearance.py`, the box in `shared/teleop/clearance_toggle.py`.

## Examples

```shell
# Drive one robot
ros2 launch husky_assembly_teleop monitor.launch.py robots:="alice" plugins:="robot_control"

# Assembly: a process, the lab obstacles and the base planner
ros2 launch husky_assembly_teleop monitor.launch.py robots:="alice cindy" \
    plugins:="robot_control process obstacles base_planner_panel" \
    process_directory:=data_design_study/260814_RobArch_support_ik

# Plan arm motions too
ros2 launch husky_assembly_teleop monitor.launch.py robots:="cindy" plugins:="robot_control obstacles arm_planner_panel"

# Try the plugin examples
ros2 launch husky_assembly_teleop monitor.launch.py robots:="alice" \
    plugins:="example_plot example_pybullet example_sequence example_ui"
```

More in the README, "Examples".

### Always on

#### `health`

Loaded by default. Shows the status of each robot and tracked object, with Unlock, Resume and Reconnect. **Parked**, after the robot's buttons and filled while on (a click toggles it), marks a robot standing still out of the way: the snapshot takes it as known where it stands (last seen, else its default pose; `stand_ins.parked`), so no Commit, Exec or Go asks about it and no planner, clearance or chip warns about it while it is not measured; it stays an obstacle there. It is unparked, with a warning, once seen moving (its base measured 2 cm or 2° from where it was parked, or an arm joint 1°) and when a plugin leases it to move it. Not kept across a restart. A chip's colour change is logged once it has held for 1.5 s, one line per row, so a flickering chip makes one line. A signal chip shows a worse level at once and a better one only after it held 1.5 s, so marginal wifi reads steadily amber.

A base's mocap chip that stays amber for 3 s opens a warning window beside the main panel (not on the phone), one for all robots: **Use refit** does what the button in `mocap_probe` does, refused while anything moves, and is greyed unless a refit is pending; **Acknowledge** closes it and the chips stay amber, for you to decide. An acknowledged reason asks again only after that chip was green for 60 s; another reason asks at once. The window closes by itself once nothing asks. A robot without a rigid body never asks.

#### `console`

Loaded by default. A window at the bottom right with the newest log lines, newest first; it starts minimized to its bar, the control at the bar's right end opens it. **Show**: **Plugins** (what the plugins say, without health's colour changes and the late-tick reports), **Warnings** (warnings from every source but the ticks), **All**; errors always show. **Source** narrows to one plugin, `health/chips` (health's colour changes), `runtime`, `robots` or `ticks`; **Hide** is a dropdown like Source in which several sources can be ticked: picking a source hides it (☑), picking it again shows it; closed, it says what it hides. They stay out whatever Show says, except their errors, and a name without a `/` also hides its topics. It starts hiding nothing; a layout file may name sources to hide at start (`plugins.console.preferences.hidden`). Messages wrap; a tick report or traceback shows in full on hover. A line under its chips shows the share of the last minute's tick periods that were late, a freeze counting for every period it lasted, and how many lines Show and Hide leave out. Pause the page (**Live**) to read; stdout and the ROS log still get every line.

#### `assembly_observer`

Loaded by default. Records everything that happens while the monitor runs, whoever does it, on this PC only, into one session folder per monitor start: `~/.ros/assembly_observer/<YYYYMMDD>/<stamp>_session/` (`_sim` added in a simulation). Days older than a week are deleted at the next start. **Copy to Drive** copies a time range after an experiment: pick the **Day**, **From** and **To** (HH:MM or HH:MM:SS; To may be `now`; **Range** fills them: last 15 min, last hour, whole day) and a **Name**; every session the range touches lands in `<Drive>/data_experiment/assembly_observer/<name>/<stamp>/` with only its events (from the newest states before the range, those lines marked `"before_range": true`), ticks and command files in that range (damaged lines and files, after a crash, are left out and counted). The copy runs in a process of its own, `scripts/observer_logs.py copy`, so it never slows the monitor; the same script also lists the sessions kept (`list`) and prints a range's events, filtered by text, robot or event (`events 14:00 14:15 --grep refused`) (make `data_experiment/assembly_observer` in Drive first, it is never made here); the line under the button says what was copied. Continuous values go into `chunk_NNN.npz`, one row per tick (60 s per file, so a crash loses at most that, a new file also when the tracked objects or the fitted bars change; compressed, values float32; read one with `load_recording(<file>)`): each base's pose, mocap noise (marker error, markers labeled and filled in, largest residual), follower errors, command, the pose it steered from, its reference and lookahead, wheel odometry, the twist still in force and battery (charge, voltage); each arm's joints, tool0, wrench, the largest |force| and |torque| since the last tick (over every reading that reaches the monitor: the robot's rate limiter forwards at most 50 Hz), the Cartesian target while the compliance controller runs, and its tool's continuous values (motor current and PWM, Robotiq position); every tracked object's pose and mocap noise; each bar `mocap_bars` fits, where its raw markers put it (its scene body's pose while shown, `object_mocap_bars_<B20>_pose`; the Rerun view draws the bar there); each stream's rate, largest gap and delay (platform and arm joint_states, mocap; read twice a second); the relay's frame drift (how far poses are off, how far Motive's frame moved by the anchors and by the truss cameras, how far the two fits disagree, the scale change in mm per metre, the anchors' residual); the share of late ticks. Every state that switches is an event in `events.jsonl`, one JSON line with its ROS time and local time, and each file of ticks opens with a line of every state then: leases, soft stops, e-stops, controllers (one event per switch, and switch errors), arm safety, robot mode and program, the follower's state, tool motor states, buttons and gripper results, battery charging and health, the relay's frame status, calibrations, deciding fit, scale flag and drift (told again per 0.5 mm / 0.1 mm/m). Mocap tracking of each base and object is told once lost for 0.5 s and back once held for 0.2 s, a stream once silent for 1 s and back once running for 2 s, each with the flickers in between. Also commands sent with who held the lease (trajectories and paths exactly as sent, each in its own file under `commands/` named by its event; holds, path stops, wrenches and tool commands inline), force sensor zeroing with the reading it tares, an arm or base starting and stopping with what started it (the lease holder, or no command sent: free drive, the pendant, a push), clearance trips with every pair and its contact, and every log line from INFO up of every plugin but health's chip colours: the guide's, the executor's, the run's, and every operator click and setting (`operator: <label>`, a value once it settled for 0.5 s). It only records, never commands. Joins the assembly run's log by ROS time.

To look through a time range, **Open in Rerun** (next to Copy to Drive) or `scripts/observer_logs.py rerun 14:00 14:30` opens it in the [Rerun](https://rerun.io) viewer, sent from a process of its own; `rerun --folder <copy>` opens a copy (one on the Drive, one of its sessions, or a folder of copies) whole, or From to To of it with start and end; `--save <file>.rrd` writes a file instead. Rerun is optional: `pip install rerun-sdk==0.39.0` in the venv (pinned: its state timelines are unstable between releases; listed in `requirements.txt`); `rerun analytics disable` turns off its usage analytics. The viewer shows one timeline in local time with a 3D view of the lab frame (each robot's labelled body box and URDF model on its base pose with its arms at their recorded joints, collision shapes hidden; each base's path; tool0, the Cartesian target while the compliance controller runs, the follower's reference and lookahead, every tracked object), the switching states as state timelines, a tab of plots per robot (follower errors, twist sent vs odometry, mocap noise, stream rates, battery; per arm joints, wrench and its peak, tool) and one for the lab (relay drift, late ticks, objects' mocap noise), and every event and log line, warnings marked. Every tick column is there under `/<serial>/<signal>/<label>` for plots of your own. About 5 MB per minute of three robots, plus about 15 MB per robot for its meshes.

### Assembly

#### `process`

At the top of the **Assembly** tab. Loads the process picked in **Folder** (the processes and old exports two folders below the Drive root, newest first, and the `process_directory` parameter's; **Rhino file** picks the `.3dm` in `assembly - demo` whose `env` or `Environment Obstacles` layer is the as-built page's room, nothing else reads it) and shows the state at one movement at a time, its planned robots in the goal blue with the Rhino obstacles that don't collide (**Process overlay**), the robots see-through at start (**Ghost robots**), and with **Unbuilt bars** the bars not built yet too; the planners load their targets from its selected step, and the run (`assembly_run`) follows it: the movement you pick with the step slider, ◀ mv / mv ▶ or an action row becomes the run's current step, except while `movement_exec` has a robot's lease for a step. The selected movement's bars and allowed contacts go into the live scene, where every planner plans, a tick after the selection; `scene_shows` says which movement the scene shows, and every plan of a process movement waits for it (`shared/process_scene/live_scene.py`). Each action row shows its mark from the run (pending, done in green, done (assumed) in orange); **▲ / ▼** scroll the rows a page, until the selection changes. After **Live IK** or a plan, the action's later movements are drawn with the joints found, on the live base they were found at (chip `joints from live IK` or `joints from plan`), and the panel turns to the target of the movement they are for; plans, runs and records never read them. Each movement shows its name in the old monitor (e.g. `J_M3_CDFM_transfer_to_approach`), a sentence on what it does, and its action's movements as a row of buttons, coloured by kind as in the Rhino repo's `docs/action_flowchart_2026.drawio` (FM, LM, CDFM, CDLM, Manual, TM), the selected one ringed: click one to select it; hovering another shows its old name and what it does. **Transfer workaround** is on at start, for this session only (runs don't keep it): Cindy's transfer runs as a free move with empty tools to the insert start, where you place the bar; while it is ticked, each jointing action is listed and drawn as it runs (`J_transit`, place, grasp, insert; the travel to load left out), and assembly_run, assembly_steps and movement_exec follow it; replan after a change. **Rhino obstacles** says what becomes of the process's own obstacles from Rhino (e.g. the cabinet): `disable` hides them, `ghost` (at start) draws them see-through, both leave them out of every collision check (base and arm planners, clearances, assembly planning); `collide` counts them in every check, and only a change to or from it needs a replan. The **build** box chooses where the build stands: x, y, z (m) and roll, pitch, yaw (°) of the process's authored world frame in the world, typed or dragged with **Gizmo** (the pink bar lines under it show where the build goes), then **Apply**. Bars, connector halves, obstacles and arm targets move; robot bases move too, projected onto the floor plane (their height kept, turned only about z); only the floor stays where it is in the lab. The chip under it shows the placement, `off the floor` (orange) when a height, roll or pitch puts the arm targets where the process's joints miss them (the live IK at the live base, such as Plan › Arm's Step IK, solves them), and `not applied` while the box holds another pose. The run keeps it (`run.json` settings `placement`) and places the build again when it opens; Apply is refused while a step runs; once an action is marked done it asks a second press (**Apply?**), since those actions were built at the old place (a New run starts clean). A newly loaded process stands where it was authored. Replan after a change. **Rhino bar lines** (off at start) draws every bar's centre line and name, pink, where the design puts it once built: a ruler of the Rhino poses.

#### `assembly_run`

In the **Assembly** tab: remembers how far the assembly of the loaded process got, in an assembly run, kept in `runs/<YYYYMMDD_HHMMSS>/` inside the process folder (not an experiment's run folder on the Drive): which actions are done, where each robot was left, the run's settings (insert split, spiral, servo by bar, the spiral's seconds and turns, and Advanced planning's free-search settings; the transfer workaround is `process`'s) and an event log. On Load it continues the newest run when it was made on these very process files; otherwise the operator chooses: **Continue newest** (the newest run, made on another export, goes on in a new run), **Continue match** (an older run made on these files) or **New run**. Nothing is written until the runs were read (a failed or stopped read is tried again). Then it selects the first pending action's first step in `process` once its robot is live; after that it follows what you pick in `process`. **Mark done** records every live robot where it is; for a robot not live, a second press records the export's end as assumed (it waits with no time limit; any other press forgets it) (meanwhile the button is amber, its label ending in **?**). **Reopen** puts an action back to pending. **New run** too needs a second press (**New run?**). **Servo by bar** is live only on a ground bar's action; on any other it is greyed and unticked (those always servo on tool0), the setting kept. Each action's mark shows in `process`'s action rows. Loads `process`. Experimental. Its writer thread also appends the as-built records to the Drive.

#### `assembly_steps`

The operator's steps, in the **Assembly** tab: the run's current step (its action's movements grouped as the operator walks them, with `process`'s transfer workaround; move between steps in `process`), **Live IK** (where the next movement starts, by IK at the live base: the insert start after a transfer, the linear move's start after an approach; logged, recorded, carried into `process`'s drawing (its blue robot moves to the live base with the joints found), and reused by the next plan while the base stays within 2 mm / 0.5°), **Plan** from the live robot through `motion_planner` (only when it is live; on a movement with nothing to plan, such as an ungrasp, a grasp or an operator step, it says so and selects the next robot movement: click Plan again), **Play** the preview timed as it will run (slider **Preview time**, opening at the motion's end), **Exec** through `movement_exec`, the **Motion time** (1–90 s, at least what the arms' limits allow), Ignore built bars (for tests in the air), **Advanced planning** (folded, saved with the run like the other settings: **Max time** per try of a free search, s; **Max iterations**; **Joint resolution** of its collision checks, rad; **Tries**; **Swept check** of the found path on or off; the same values govern a transfer, the way home and the support moves), and the **Plan plots** window at the bottom left, minimized to its bar until a plan arrives, when it opens by itself (close it with the control at the bar's right end): every joint along the preview (deg) and the largest joint step between the plan's rows (deg); the old monitor's bar-hold drift plot comes later, with the held moves. **Check tool0** draws each flange's live tool0 (mocap base + FK, red) against the step's authored target (blue) with a line between them, says the gap per side (mm, and degrees per axis) and records it (`check_tool0`); nothing moves. A retreat is planned to the live tool0 poses backed out along their own -z, as the encoders read them (the run's **Retreat live axis**, on by default; off: the export's axis), logged as `[retreat live]` with each tool's angle from the Rhino axis (a warning over 20°) and recorded as `goal_live`; when the full line is blocked it plans a shorter one, 5 mm at a time down to 25 mm, with a warning. **Visual diagnosis** (settings, off at start, this session only) draws the real robots see-through and, after each insert or retreat plan, its tool0 path in green with the Rhino (blue) and planned (red) start and end frames and the gaps between them, logged as `[visual diagnosis]`. A transfer, an approach or a ground bar's insert ends with its servo (the step line says "then servos … onto the insert start"), which Exec runs alone once the step's other parts are done. An insert after its transfer's mocap-bar servo is planned from where the servo left the flanges (logged as `[insert plan] MoCap-bar correction carried`, recorded as `goal_carried`). After the action's last step it says to Mark done (assembly_run's button). Live IK and Plan wait until the live scene shows the step (`process` puts its bars a tick after selecting it) and are refused when another step is selected meanwhile. A plan goes stale when the process, the step, the transfer workaround or the run's statuses, the acting arm (2°) or base (2 mm / 0.5°), or another robot (1 cm / 1°) changes, and is used by one Exec only. Loads `process`, `assembly_run`, `motion_planner` and `movement_exec`. Experimental.

#### `movement_exec`

In the **Assembly** tab: runs one step on the real robot with the old monitor's Confirms: **Exec** sends a motion along the plan at once (timed for the arms, its time and largest joint travel logged, rebuilt from the live joints and sent right after the last check; with other robots not measured, **Exec** asks for a second press, as **Commit** does). **Clearance** below Exec, ticked, runs such a motion under a clearance that soft stops the robot once it touches anything and refuses a start in contact (contact only: the assembly planner checks no margin, which an amber "small clearance" chip says); none with **Ignore built bars** ticked (amber "no clearance" chip), nor for the inserts, retreats, handoffs and servo passes, which touch by design ([Clearance](#clearance)); a Robotiq open (0.426) or stiff close (0.8), a step by hand (the bar placed and clamped with the tools' own buttons: one prompt for both; the travel to load, or the transfer workaround's transit with empty tools to the insert start, zeroes the force sensors at its end, before the bar is mounted) and the servo's first pass wait for **Confirm** (there or on the phone's **Exec** tab), the prompt naming the robot; and the parts that run partly compliant (`shared/execution/`), sent at once too: the INSERT (rigid under joint control up to the split, then the last millimetres under the compliance controller along a straight line or a 15 mm spiral while the mating joint screw tightens, until it stalls or 30 s pass; Spiral's box is live on every bar's action but a ground bar's; after a stall of a bar with one mating joint, the other arm finishes at its line's end under compliance, off the spiral too, settles against the force (≤ 3 s) and switches back; a ground bar is always rigid with no tighten, every other bar always rigid then compliant: no setting changes the mode), the RETREAT (the old monitor's stiff screw-out: under the joint controller throughout, both jaws LOOSEN while the tools back straight out 12 mm at the screw rate, 2.4 mm/s, then the rest of the planned line rigid, the tools STOPped at the end; the path checks logged PASS/FAIL before anything is sent, and the arms over 0.57° from the plan's start refused; with the run's **Retreat compliant**, for tests only, the gripper screws open, the force sensors are zeroed, a compliant break-out of the first millimetres, back to joint control, then the rest replanned from where the tools are), and the Robotiq HANDOFF (the arm goes compliant before the close, giving way up to 10 mm; a stiff close when its frames disagree). The run's settings (`assembly_run`'s) shape them: Insert split mm (0–30; a compliant retreat's break-out too, from its start), Spiral, Spiral s (1–60) and Spiral turns (1–10); a spiral over 50 mm/s is refused at Plan. After a transfer, a support approach or a ground bar's insert the step ends with the servo (`servo_part.py`): pass by pass, each planned on `motion_planner` from the live arms (IK at the live base; a straight bar-held line for two arms, two rows for one), the first pass after Confirm (plain) and any later one travelling over 5° after a warning's Confirm, up to 8 passes, until both flanges are within 0.2 mm of the authored targets or the next move would be under 0.2 mm (tool0: with the bar in both tools each pass aims the one rigid move that best fits both targets, because a held move can only keep the flanges' relation; what is left is logged, with a warning over 0.5 mm, and the correction is carried into the insert's plan) or, with the run's **Servo by bar** (on by default; it steers only a ground bar held in the tools, every other bar servos on tool0; with no usable fit a warning window asks **Give up** or **Tool0 servo**) and the bar's markers streaming, until the bar's mocap fit is within 0.5 mm / 0.1° of its design pose; a transfer's bar correction is carried into the insert's plan; after a ground bar's insert straight lines only, stopped when a flange's force changes by over 20 N, and only with the flanges within 3 mm of the insert plan's end (the request's own, or, for a servo sent alone, the insert the executor ran last for that step and robot). One panel line shows each pass's errors, and each servo is recorded as `runs/<run>/servo/<action>/<movement>.<n>.json` with a .png of its readings. Refuses another robot's or another movement's plan, a stale plan, a plan made before a servo moved the arms, a robot not live or soft stopped, an arm the safety sync (`multi_arm_safety_sync`) does not vouch for (no recent status, not operational, or its program stopped: press Resume), a compliant part whose arm is not under the joint controller or whose measured TCP is over 10 mm / 2° from the URDF's tool0; refused too while another plugin leases any robot (a teleop drive, a committed plan, a base experiment). Leases every robot while it works: no other plugin gets a lease, so nothing else here moves any robot (one motion at a time), and before sending and while its arms move it checks that nothing else moves (another robot's arms or base, or one whose states went stale); Hold in `robot_control` stops its motion short of the end. **Cancel** (or Stop all) holds every arm; in a compliant part it also STOPs the tools, holds each arm at its TCP and switches it back to the joint controller. A hold an arm refuses (stale joint states) is said loudly: HOLD NOT SENT, stop it with the pendant or the e-stop; a switch back not confirmed within 10 s is said loudly too: ARMS MAY BE LEFT under the compliance controller, switch them in `robot_control` before anything else. The teach pendant's speed slider must be at 100 % (slower, a motion times out and is held mid-path). **Dry run**: every check, nothing sent. Every part is recorded in the assembly run (`runs/<run>/movements/`; each record keeps the ROS time and the robot's base at the part's start and end; a compliant part's record keeps its plan and settings, phases, switches, stall times, peak force, end errors, the retreat's checks and tail, and one sample per tick). The **Exec plots** window at the bottom left, minimized to its bar until a servo or a compliant part starts, when it opens by itself with that kind's plots (close it with the control at the bar's right end), shows the running servo pass by pass (tool0 position and rotation errors per side, the base's drift, the mocap bar's deviation, the force change; a chip says which phase the pass is in, and under each plot stand the last pass's numbers) or a compliant part's force and torque per arm each tick; the curves stay until the next part of that kind. Each servo pass and a retreat's replanned tail wait until the live scene shows the request's step, and a pass is refused (nothing sent) when another movement is selected meanwhile. Loads `motion_planner`, `assembly_run`, `mocap_bars` and `process`. Experimental: the first plugin that runs process movements on the robots, e-stops in hand. Around every part (the start of a request's first, the end of each) it measures every MoCap bar through `mocap_bars` and appends an as-built record to the day's file on the Drive (`shared/runs/as_built.py`; **As-built: record now** any time); the `doc` plugin builds the day's pages from them.

#### `assembly_guide`

In its own **Assembly guide** tab, beside the Assembly tab: the whole schedule part by part, each part run by the layer below it, starting at the movement selected in `process`. The parts of an action: first one **park** per robot the action does not use and that holds no bar at its start (Settings › **Park idle robots**, on: its arms stowed at park.yaml's joints by `arm_planner`, then driven to its parked pose by `base_planner`; done, with nothing to move, when it stands parked and stowed already; a simple rule for now: a robot parks even when the next action needs it again; actions by hand park nothing; parks are optional: one that cannot stow or drive warns and is left amber **not parked** (Auto goes on; a soft stop, a Go not given or a motion not over in time stop it as any part), Done leaves one with one press, and a park not done never makes a later part ask twice, the needs line warns **not parked** instead), then the **drive** to its start (`base_planner`; the robot's follower drives; none for a robot that holds a bar at the action's start: it stays at the bar), then the executor's own parts of each step (`movement_exec`): each arm **move** (a transfer or an approach to the goal solved by IK at the live base; a free move (a transfer with empty tools, a way home, an approach, a leave) planned by `arm_planner`, both arms in one search, 1 cm from everything; a held transfer, the lines, and a free move without a target or joint goal in the process by `motion_planner`; a free move the arm planner finds no goal or path for fails at once, without trying `motion_planner` (it would fail too, after minutes; Auto and God search 3 times first); Settings › **Free moves on the arm planner** turns that off), the bar placed and clamped **by hand**, the **servo**, the **insert**, the **servo** after a ground bar's insert (a part of its own: the executor gates it on the insert it ran last), the **retreat** (its ungrasp with it), the **gripper** steps; then **Mark done** (`assembly_run`). Every plan (the drive, a goal by IK, every move) waits until the live scene shows the part's movement (`process` puts a movement's bars and allowed contacts into it a tick after selecting it) and is refused when another movement is selected meanwhile. It works like the calibration guide: one part shows, and Prepare, Go and Done act on it; **Back** and **Next** show another (and select its movement in `process`, so Plan › Base's **Load: Step** and Plan › Arm's **Step joints** and **Step IK** load its target), and whatever runs goes on. At the top, the part shown in a light blue card: its action and number in grey with its kind and robot as small pills, its name large, and its goal in a line; under it, the shown action's parts as numbered chips, as in the calibration overview: the fill is the result (green done, amber skipped, red failed, grey to do), the part shown is ringed black (and bold in the parts list below), ▶ marks the part whose procedure runs, and the earlier parts the shown one needs that have no result yet are outlined dotted black. The next part to do is not marked: it is the first grey one. Under Back, Next and Redo from here, three lines of chips for the part shown: **needs** (its robot live, not soft stopped, not held by another plugin; the parts before it done; the executor free; the planner that plans it: base, arm or motion, amber when a free move went to the motion planner, having no target or joint goal for the arm planner; red **plan stale** once a plan waiting for Go no longer fits, for the reason the executor would refuse Go), **live** (every robot still or moving; how far the base or the arms still are; the boxes ticked), **result** (the executor finished it, the robot at its end, the run's mark, skipped); then **guide**, the guide's own line (the mode, what runs and where, e.g. "B20_J part 2 waits for Go" while another part shows, what Auto waits for, why Auto or God stopped, until the mode is chosen again, and how the part shown last ended: a failure stays with its part while others show). A procedure belongs to the part that started it: Go and Preview act only there, Cancel anywhere. A press that cannot act says why: an amber chip first on the guide line and the reason below the buttons, "… refused" for 8 s, or "…: press again" while a second press may come (5 s; the button then reads **Go?**, **Done?**, **Skip?**, **Auto?**); only Go without a question, Prepare and Go on a part Done confirms, Back and Next at the ends and Cancel with nothing running are grey. **Prepare** and **Go** are for parts that move a robot: Prepare plans the part (or opens the executor's question), the ghost previews it (**Preview time**, **Play**), Go sends it or answers the question before the robot moves (the phone's Exec tab answers it too; a drive or stow already sent with Commit in Plan › Base or Plan › Arm is not sent again: Go waits for it, and plans the drive again if it ended away from its goal), **Cancel** stops it, every arm holding. A part by hand and Mark done are confirmed with **Done**, Prepare and Go grey: a part by hand once every box of its checklist is ticked (what the executor asks, e.g. Bar placed, Screws clamped, and Hands clear), when the executor records it; Mark done marks the action in the run once its robot stands still (at most 20 s, then Done twice marks it anyway). Each kind of part has its own folder below the buttons (the drive's target, the move's goal and **Motion time**, the boxes by hand, **Servo by bar**, the insert's split and spiral, the retreat's live axis: the run's settings, shared with the Assembly tab; **Rehearse**, a dry run of that part only), and under it the part's description: a blue **what to do** line, then one light card with the buttons to press, in order, **Check** (only what that part needs), and in grey **Fix by hand** (the fix one layer down in Plan › Base, Plan › Arm or Control). A part is done by its result: the executor's finished movements, whoever sent them (an Exec in the Assembly tab counts), the run's mark, a drive that ended at its goal (or whose action's later parts ran). A part that finds no goal by IK at the live base flags the drive before it red **not good**: that drive is to do again, and its Prepare drives even when the base already stands within 6 cm and 6° of its goal. The run's log keeps what the executor finished and forgot, so a restart, or continuing the run, shows the parts done again. In Mode Off the guide stays on a finished part, its result in the chips, until **Done: next part**, which shows the next part not done yet, past those done already (the log names them; Back and Next still step one part); a part whose robot already stands at its end (a fix by hand: 6 cm and 6° for a base, 1° per joint for an arm; a goal solved by IK at the live base counts only while the base stands where it was solved) goes on with one Done; any other part asks a second press (**Skip?**); a part by hand and Mark done are never skipped, but Done twice confirms a part by hand with boxes unticked, or Mark done whose robot is not live (the run then assumes the export's end), each with a warning in the log. **Prepare** twice on a done part does it again, only that part, its later parts kept (a drive drives, a move moves, even when already at the goal), also in an action the run has marked done (the mark stays; Redo from here reopens it). Prepare or Done on any part replaces a procedure that only waits for Go, Auto going on. Out of order, with earlier parts of the action not done, Go and Done ask a second press (**Go?**, **Done?**); with other robots not measured as well, that one second press of Go answers both. **Redo from here**, while nothing runs, on a second press, with anything from the part shown on done (or boxes ticked on the part by hand shown), makes it and every later part to do again: the run reopens every action marked done from its action on, the executor forgets what it finished from the part on, the boxes of a part by hand are unticked, and a drive, move or park whose robot stands at its end then counts as done (and is skipped) only once it ran again, one Done accepted it, or the robot, measured live, left that end and came back; nothing moves. A new run, or an action reopened in the Assembly tab, makes its parts to do again. **Mode**: **Off** (you press Prepare, Go and Done); **Auto** (works on the next part to do from the part shown when it was switched on, skipping parts already done: shows it, prepares and sends it, waiting at every question of the executor, at a plan with a warning, at every part by hand, and, on real robots, at every drive and move: there Auto only prepares; a second press turns it on); **God** (Auto that answers every question and ticks every box too, and goes on past warnings: only while every robot's base, arms and tools and the relay announce themselves simulated, checked every tick and before each answer). Auto and God end on a failure, a refusal, Cancel, a soft stop of any robot, another plugin's lease on the robot, a part that ends without a result, a movement picked in `process`, the parts built again (a setting or the process changed; never while a part runs), or a Mark done with a doubt (Auto never marks past one: parts before it not done, its robot not live); the guide line says why. Every start, end, skip, redo, out-of-order Go and mode change (with why Auto or God ended) is a `guide` event in the run. Loads `process`, `assembly_run`, `base_planner`, `arm_planner`, `motion_planner` and `movement_exec`; load `base_planner_panel`, `arm_planner_panel` and `robot_control` too, for the fixes. Experimental, not yet tried on a robot.

#### `motion_planner`

In **Plan › Motion**: plans process movements, solves their goals by IK and checks collisions for other plugins, one request at a time on one worker thread with a compas_fab world per robot (the first request for a robot loads its models, up to a minute); **Cancel** stops them; optional PyBullet window (a tab per robot, icon and id as in Control; one window, so ticking a robot moves it there). What the last answer collided with (a start, a goal, a swept segment, a linear step) shows in the collisions panel. While a free search runs (tamp's dual-arm birrt: a transit, the transfer workaround, the way home; or a support robot's one-arm birrt: its approach and leave), **Search tree** (on) draws it every 2 s at the moving arms' tool0s: the tree grown from the start (blue) and from the goal (purple), a yellow line labelled with how far apart in joint space their closest nodes are, and, for tamp's search, the configurations checked since the iteration began as dots (red where they collided); the panel, and the Assembly tab after "planning …", say the try, birrt's run and iteration, that gap and the nodes, and each run's end is logged. **Search tree legend**, a folder at the bottom of the panel, explains each mark and term. A found path takes the drawing away; after a failure the trees stay until the next search. birrt draws only as many nodes of the bigger tree as the smaller one has, so its newest nodes show later. Recording costs about 0.1 % of tamp's search and 1 % of a one-arm one (a fast search records an iteration every 0.5 s). Loads `collisions`. Experimental.

### Driving and planning

#### `robot_control`

The **Control** tab, with a tab per robot: drives the base, jogs each arm joint by joint while a button is held, or its tool0 along or about one axis of the **Frame** chosen (Robot: x forward, y left, z up, whatever the flange's turn; Tool: tool0's own) (the **Tool0** buttons, at the **Tool speed** in mm/s; one arm at a time, a point streamed every tick 0.2 s ahead on a line from where the button was pressed), moves it to a Cartesian target (sliders or gizmo, in the husky's base_link) with a compliance force, holds it, operates the tools. An arm's **Joint arrows** box (below the joint jog) draws in the 3D view, while the joint controller runs, two curved arrows per joint around its name, red the way its + button turns it and green the way − does, each marked + or −; its **Tool0 arrows** box (below the tool0 jog) draws at tool0, per axis of the chosen **Frame** in its colour, a straight arrow the way + moves it and a curved one the way + turns it, long enough to reach out of the tool. To move an arm to a pose, plan it in `arm_planner_panel`. Free drive is the arm's **Free** controller: the arm can be pushed by hand only while its **Free drive (hold)** button is held or **Keep on** is ticked. Each arm's **Live plots** folder (closed at start) shows its raw force and torque over the last 30 s.

#### `base_planner_panel`

In **Plan › Base**: plans a collision-free path for a base around the other robots and scene bodies, keeping the **Margin** (m, 10 cm at start; a request from another plugin, e.g. the guide's drive, keeps 10 cm too) from everything but what its start or target is already closer to, which keeps as much as it has there (the plan's line names it); with the Lattice algorithm, where nothing keeps the Margin it may come as close as the **Narrow margin** (Advanced, 5 cm), dearer, and the base drives slower there (as close / 1 s, ramping at 0.1 m/s², sent as `BasePathScaled` to a follower that takes it, else the whole path at the slowest speed; the path on the floor shades to amber where it drives slower); a target with less room than the Margin moves up to 4 cm and 4° to more room (the plan's line says so), and the search runs from the tighter end first, then the other way, 20 s each (Commit's clearance soft stops the base within 5 cm, or half the Margin below 10 cm, with an amber "small clearance" chip; it refuses a start already that close, and the "starts too close" chip warns before the press; **Clearance** below Commit, unticked, drives without it; with another robot not measured Commit asks twice: [Clearance](#clearance)), with the algorithm chosen under Advanced (each with its settings, and a Debug view that draws how the search worked); Commit sends it to the onboard pure pursuit follower (`crl_husky pure_pursuit`, or a simulation in your own ROS domain, never 80: [simulation_manual.md](simulation_manual.md)), which drives it at once if the velocity controller is active. A blue ghost stands at the target (hidden once the robot is there) and a green one rides the planned path. The floor shows the path as the follower cuts it and the robot's trail, until another base is sent a path or 30 s after the run ended; with Record ticked each run is saved to `data_experiment/base_planner/` on the Drive (`drive_root`, create the folder in Drive first). Loads `base_planner`, the headless planner it drives (other plugins can request and commit plans through it too: such a plan, the guide's drive, shows here as if planned here, the robot and target set to its own, its ghosts shown, and Commit sends it), `process` and `collisions`. Experimental.

#### `arm_planner_panel`

In **Plan › Arm**: plans a collision-free arm motion to a joint target (the arm now, its stow pose, the process step, or sliders) and sends it as one joint trajectory that runs through rounded corners and rests only where a corner cannot be rounded clear of collisions; the preview shows the same timing, and **Slow down** (×1 to ×5) stretches it without replanning, for the next plans too. A path keeps 1 cm from everything, more than the 5 mm at which Commit's clearance soft stops it; when the arm starts or ends closer, the path keeps as much as they have, the plan's line says so in amber, and the clearance is half of that (an amber "small clearance" chip). **Clearance** below Commit, ticked, runs the path under that clearance and refuses a start already that close (a red "starts too close" chip says so before the press); unticked, nothing soft stops it (the chip turns amber); [Clearance](#clearance). Commit does not ask twice for another robot whose only unknown parts are arms beyond the planned arm's reach (about 2.5 m between shoulders, `world/arm_reach.py`). The panel for the headless `arm_planner` plugin (loaded with it), which others can use through `ArmPlannerContract`; also loads `process` and `collisions`. Experimental. Two Load buttons take the target from the step selected in `process`, for the arm chosen when the step moves it (else the first arm it moves, and the line names the others): **Step joints** loads the joints the process gives the step's target (else its start), as authored; **Step IK** solves the step's tool0 frame by IK at the live base, the solution nearest those joints, so a fix planned here ends where the step's own move would, not a base error away (only for a step that gives the arm's tool0 a frame, such as a transfer or an approach; no solution, no target). Through its contract the planner also plans several arms of one robot in one search (`ArmPlanRequest.also`: Cindy's two arms, each keeping clear of the other) and solves several arms' goals together (`solve_goals`); it always plans in the live scene, as it is now, since the plan runs on the real robots. In the panel, **Arm: Both** (a robot with two arms) plans both in one search, in the live scene: the target comes from **Load** (Now, Stow, Step joints, Step IK; Step IK solves both arms' tool0 frames together at the live base), the sliders show the first arm's, greyed. A plan another plugin asks for (the guide's free moves, calibration's) shows here as if planned here: robot, arm (Both for two) and targets set to its own, its ghosts shown, and Commit sends it. The mount splits each arm's shoulder lift turn: no path passes pointing down (+90°, the same as −270°: the upper arm into the platform), so the planner keeps the lift within −270° to +90°, and refuses a target beyond at once (the same pose is a whole turn the other way); goals by IK in the guide and the motion planner turn the lift into that range. A search that finds no path logs what blocked it (the share of its checks blocked, the pairs blocking most, the joints that turn most) and saves its scene and request to `~/.ros/arm_planner/<YYYYMMDD>/<HHMMSS>_<robot>/`: `scripts/replay_arm_plan.py <folder>` runs it again offline (`--set JOINT=DEG` tries another goal, `--window` shows it in PyBullet).

#### `obstacles`

The lab's obstacles as collision bodies for the planners: tables, cabinets, tripods and trusses, and walls around the usable floor, from the lab file `data/lab/<lab>.json` (in git; `lab:=<name>`); and the floor, a slab under z = 0 out to the walls, not drawn, which arms, tools and what they hold collide with while the robots' platforms (wheels, chassis) may touch it. Click an obstacle in the 3D view or pick it, then drag it with the gizmo (only yaw is kept), resize it with the corner gizmo, or type position, yaw and size; rename and remove it, and set the border's x and y range. Edits stay unsaved (amber chip) until **Save** writes the lab file; **Revert** goes back to it. **Add** puts temporary boxes and cylinders (purple) into the scene, kept in `~/husky_obstacles_temporary.json` across restarts and never in the lab file; **Promote** moves one into the lab.

#### `collisions`

In its own **Collisions** tab: lists what collision checks hit, per source (calibration takes, a failed arm or base plan, the motion planner's last answer, base_exp's blocked way back), and draws the ticked hits as they were checked: what moved solid red, what it moved into see-through cyan, the deepest contact with its depth; Focus adds every robot as checked, faint; each drawing goes after 2 minutes, its hit unticked but still listed. "As checked" shows meshes as the convex hulls compas_fab tests. Clearance trips of any plugin (a driven robot stopped for coming within its margin of something) come under **clearance**, the newest ticked, with the gap as "x mm apart". Loaded by calibration, the arm and base planner panels, motion_planner and base_exp; load it by name to see clearance trips with other plugins. It only draws: it sends nothing to a robot.

#### `stop_recovery`

Loaded by default. In its own **Stop recovery** tab in the strip, with a short guide at the top and a block per robot with arms. It logs every rest pose of each robot: all its arms, once the robot stands after moving while every arm ran (operational), with tool0 and the force vector; never what an arm does while it is not running or just before a stop is reported, so an e-stopped arm sagging on its brakes leaves the pose from before the stop. It also logs each stop (the safety sync's reason, the forces then). Poses and stops go to `~/.ros/stop_recovery/<YYYYMMDD>.jsonl`, marked sim or real, and are read back at start (today's and yesterday's); a real robot is offered only real poses, a simulated one only simulated ones. **Pose** offers the newest five, newest first; picked is the newest one a Go back did not end at (one followed by a stop says "before stop hh:mm:ss", one a Go back ended at "Go back ended"). The readout shows per arm how far it is from the pose picked (largest joint step, tool0) and how far its force is off its force then (the difference of the raw vectors: the sensor's offset and the tool's weight cancel, unless the sensor is zeroed in between). **Go back** asks first and on its second press sends one slow joint move there (at most 2°/s, at least 8 s; a two-arm robot's arms together), under the robot's lease and without a collision check, then waits for the joints to arrive. It is refused while the robot is soft stopped, an arm is not operational, not under the joint controller, moving or without a force reading, and for more than 3° on a joint or 20 mm at tool0 (plan that with `arm_planner_panel`). The robot is held at once if an arm's force goes 5 N further off its force then than at the start, or if the arms are not back within twice the move's time plus 5 s (the pendant's speed slider below 100 %); **Cancel** holds it. When a robot with arms runs again after a stop, a window opens with its Pose, readout, **Go back**, **Cancel** and **Done**, so the tab need not be found; it closes on **Done** (refused while it moves back) or once the robot rests somewhere else after other moves. Back, the message gives each arm's force off before and after. It never touches a tool: after a stop while holding, do not zero the force sensor, open or reactivate the gripper, or restart the robot's launch (the Robotiq activates, opens and drops what it holds). After an e-stop the arm comes back on the pendant (ON, then START); after a protective stop with Unlock in Health.

### Mocap

#### `mocap_streams`

What Motive streams right now, in **Mocap › Streams** (and as a **Streams** tab on the phone). Read-only: it commands nothing and takes no lease. The top chip sums it up ("3 of 4 expected streaming"), in the worst row's colour, the line below it names the rest ("stale: probe; missing: Belle"); the next says the relay's frame status and how far Motive's frame moved. The table fits the panel, with no sideways scroll. Then a row per rigid body: the robots' bases and every tracked object (the probe), then anything else the relay lists, added below and kept once seen (the bars' Motive assets too: bars are fitted to the raw markers, see `mocap_bars`). Each row has its id, what it is (a body nothing expects shows its name in Motive), a state chip, valid samples per second as they reach the monitor (the relay's 50 Hz while live, not Motive's frame rate), the mean marker error in mm, and how long it has been in that state.

**live**: amber when the mean marker error is above the mocap chip's 1 mm. **stale** (red): no sample captured for over 1 s, though the relay keeps republishing the last one; the time counts from that capture, so a dropout noticed late, or across a monitor restart, still reads "33 min". **invalid** (red): samples come, but Motive lost the body or the relay marks the pose invalid. **missing** (amber): expected, no sample since the monitor started. **extra** (blue): the relay lists it, nothing here expects it; no numbers, as nothing subscribes to it, and grey **stale** once the relay stops listing it. Asks the relay every 2 s without waiting (`/mocap/get_streaming_ids`). Loads `process` and `mocap_bars`.

#### `mocap_bars`

In **Mocap › Bars**: fits every bar of the loaded process that carries markers to the relay's raw markers (`/mocap_relay/markers`, every marker Motive sees, labeled or not) within 80 mm of where the bar should be: where the live scene has it (a built bar at its assembly pose, a held one on the flange), else its assembly pose. Motive's bar assets and labels are never used: Motive mixes up bars that look alike. A bar up to about 6 cm (and a few degrees) off is found; one farther is not: the fit is a check of the plan. Each bar's CAD markers (from the markers on its connector halves) are fitted with the bar fit of `shared/bars/layouts.py` (the matcher in `world/marker_match.py`): matched by their pairwise distances, around the last fit or where the bar should be, ten times a second at most and one full search per tick across the bars (a bar with under 3 markers near it fails at once; one the live scene lacks, not built yet, is only matched around its assembly pose with every marker, never searched among its neighbours' markers; once found, a bar is followed with a marker hidden), markers with a residual or size out of range left out. Every bar is a scene body `mocap_bars/<B20>`, the bar and its connector halves see-through in the old monitor's MoCap cyan at its fitted pose, shown while its fit is under 0.5 s old; visual shapes only, so never an obstacle; the observer records it every tick. The chip says whether the markers arrive; **Show markers** draws the chosen bar's nearby markers (green matched, amber the others), fitted and planned markers; **Raw markers** every marker the cameras see; **Arrows** (off, chosen bar, all bars) draws the as-built report's arrows from where the bar should be to its fit: the gap at its start, middle and end (green up to 2 mm, amber up to 5 mm, red beyond, as the frame check), the planned axes (faint) and fitted ones with the turn about each as a purple arc, both **Magnify** times larger (20 by default), the labels the true mm and degrees; **fit settings** set the search radius (80 mm), fit period (0.1 s), marker age (0.5 s), hint age (1 s) and search retry (1 s) for this plugin's fits and so the as-built record's (each record keeps them under `options.mocap_fit`), not the servo's; the axes and arcs sit at the bar's middle as in the report, and with **all bars** turns under 0.01° get no label; the stats block below the buttons reads the chosen bar's fit the old monitor's way (each marker's Motive and fit residual, each plate's ball pair and roll, the spacing between plates, the bow, the deviation from the planned pose), and **Measure + log** / **Log live** print the old `[mocap bar]` report lines; **Record take** saves the chosen bar's fit to `data_experiment/mocap_bars/<experiment>/` on the Drive. Offers every bar's latest fit and a fresh fit on demand (`MocapBarsContract`, for the as-built record). The servo part steers on its own fit of the held bar with **Servo by bar**. Loads `process`. Experimental.

#### `frame_check`

How far the built frame is from its design, live, in **Mocap › Frame** and as a **Frame** tab on the phone: for straightening the frame by hand while watching the phone. Read-only: it commands nothing and takes no lease. Every bar that carries markers and that the live scene shows built at the selected movement (select a movement after the bars to check; a bar held by a robot or not built yet is left out) is compared with its assembly pose (placed) at both ends, from `mocap_bars`' fit; a fit older than `mocap_bars`' **Marker age s** (0.5 s by default) counts as none (a hand over the markers greys the bar out). The chip names the worst end, e.g. "worst B21 top 31.5 mm". The picture is sent again only once an end moved over 0.3 mm. The picture shows the frame from the **side** (seen from +x), the **front** (seen from -y) or the **top**, the design in grey and each measured bar over it coloured by its worse end (green up to 2 mm, amber up to 5 mm, red beyond: `shared/bars/pose.py`'s `bar_gap` and `gap_color`: the as-built report's numbers and 5 mm limit, the colours of `mocap_bars`' **Arrows**), the errors magnified **×1**, **×10** or **×30**. Below, with **All**, each bar's worse end, its distance and the bar's tilt; with one bar chosen, per end (bottom/top for a post, -x/+x end for a lying bar) how far to move it to its design in world x, y, z (mm), and its tilt. Bars without markers are not measured. Loads `process` and `mocap_bars`. Experimental.

#### `mocap_probe`

Tracks the probe and records points with it, e.g. obstacle corners; exports JSON and loads it back. Shows its state in a separate panel, see [Panels](#panels). In the closed **Debug** folder: **Map coverage** keeps the probe's position and marker error every tick while you walk, and draws a map smoothed from them on the floor (15 × 15 m, centred on the mocap origin) by the mean marker error: green, deeper the lower, up to the mocap chip's 1 mm; amber → deep orange up to 2 mm; red above; greyer where the probe was often lost, grey where never tracked, nothing where you did not walk. Export and load the samples as JSON. **Floor calibration**: floor points, the marks and Motive's anchors place the lab frame on the floor, exported for the relay to apply, on the laptop and the phone: [floor_calibration_manual.md](floor_calibration_manual.md). **Show cameras** (also in **Debug**): Motive's cameras where its calibration puts them, each a wireframe of its view with its name, its view's edges as faint rays down to a plane at a chosen height and a cross where its aim meets it, from the mocap relay; **Views on the floor** colours the map's area by how many cameras see each point of that plane, each region outlined with its count (grey none, red one, to green for six or more; range and occlusion not modelled).

### Calibration

#### `calibration`

Calibrates a robot's base rigid body (`base_mocap_from_base_footprint`, what the mocap relay applies) by sweeping one arm's first two joints, guided step by step: Setup, Marker error (drive with the D-pad; refine in Motive if too large), Sweeps (collision-checked by the arm planner; the colliding takes are listed in the **Collisions** tab), Record (each take planned to its start, then sampled once still), Solve (the old pipeline's math), Validate, Apply (reloads the relay), then optionally Tip offset and Punch, and an Overview of the result and its figures; the session goes to `data_experiment/calibration_data/<date>/` on the Drive, where the relay finds it. Next only once the step's checks pass. Progress is saved after every change: after a crash or restart, choosing the arm offers to resume its unfinished run. The takes are predefined, taken from the old monitor (`data/calibration/sweeps.yaml`); a simulated robot's sessions stay in `<Drive>/data_experiment/sim/calibration_data/domain_<ROS_DOMAIN_ID>/<YYYYMMDD>/`, where the relay finds them for a fake Motive's bodies ([simulation_manual.md](simulation_manual.md)). `scripts/solve_calibration.py` solves a session again offline, and with `--old-scripts` compares it with the old pipeline's scripts run on it. Loads `arm_planner` and `collisions`. Experimental, not yet tried on a robot. How to run: [calibration_manual.md](calibration_manual.md).

### Experiments

#### `base_exp`

Drives test paths (straight, turn, arc, sine, drive-turn-drive; geometric or timed) from where the base stands with the onboard pure pursuit follower, with live error plots; the monitor measures every run's errors itself, the same for every controller, and keeps recording until the robot settles; each run gets its own folder under `data_experiment/base_exp/<experiment name>/` on the Drive (`drive_root`) with its setup (sim or real, sim model, controller and parameters) and outcome (experiment.json), the recording (.npz), and once reported its numbers (report.json) and an overview plot (.png). **Start auto** runs paths at one fixed speed, the standard paths (the same 10 in every scenario, resumed per experiment and setup) or random paths from a grid of distances and angles, or constant commands open loop over a grid of speeds and turn rates; each run is checked to keep 0.3 m from every robot and scene body (`obstacles` loads with it, for the lab border; so does `collisions`); during any run the robot is soft-stopped and automation paused if it comes within 5 cm of anything, and a run starting that close is refused, nothing sent (always on, no box); with the robot's arms or another robot not measured, Start and Start auto ask for a second press ([Clearance](#clearance)). Experimental; needs `crl_husky pure_pursuit` on the robot, or a simulation ([simulation_manual.md](simulation_manual.md)). Analyse the runs with `scripts/analyze_base_exp.py`: `summary.md` compares the controllers, `robot_model.md` fits a model of the robot, `constant_commands.md` shows how it changes with speed and turn rate. How to run: [base_exp_manual.md](../experiments/base_exp_manual.md).
