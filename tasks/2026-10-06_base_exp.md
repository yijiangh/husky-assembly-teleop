# Base experiment: pure pursuit follower and the `base_exp` plugin

Port of the crl-husky base MPC experiment (matplotlib `mpc_trajectory_ui` / `mpc_live_viz`) to the monitor,
with a new onboard pure pursuit follower first. The MPC stays as it is until its maths has been checked.

## Decisions

- One path message for any base follower: `crl_husky_msgs/BasePath`. It holds x, y and **unwrapped** yaw, plus an
  optional `t` array: with times the path is timed, without them it is geometric. An empty message stops the follower.
  Status comes back as `crl_husky_msgs/BaseFollowerState` on `<ns>/base_follower/state`.
- Shared path model `crl_husky/follower_path.py` (numpy/scipy, no casadi). The poses are cut into pieces:
  - a **drive piece** is an interpolating cubic through its points, split where driving switches between forwards and backwards;
  - a **turn piece** is a run of poses on the same spot (within 1 mm);
  - a final turn is added to reach the last yaw.

  The follower tracks this model and the monitor draws it, so the preview is what the robot follows.
- Pure pursuit (`crl_husky/pure_pursuit.py`, node `crl_husky/onboard/pure_pursuit_node.py`):
  - The lookahead point stays within its piece, so corners are not cut. The robot turns on the spot first when that point is more than 60° off its heading.
  - Geometric runs brake to stop at the end of each piece.
  - Timed runs follow the pose due at each moment: due speed plus a correction for lag, still braking for stops. A piece does not end before its due time.
  - The follower aborts when mocap is lost, or when the robot is more than 0.5 m off the path.
  - It publishes `cmd_vel` only while following, so the D-pad (teleop) still works when it is idle.
- MPC reference (`reference_path.py`): the spline is now 3D, (x, y, unwrapped θ), instead of the 4D (x, y, cos θ, sin θ) version. Turns on the spot now advance at a constant rate at any angle.
- Recordings are monitor `.npz` traces (`Trace.save(path, extra)`), with the path that was sent stored in the same file.
  Each run gets a folder `<Drive root>/data_experiment/base_exp/<name>/<date>_<time>_<robot>_<template>_<sim|real>/`
  with `recording.npz`, `experiment.json` and `overview.png` (`plugins/base_exp/report.py`, modelled on the old
  `_overview.png`). The setup is read at Start: sim when a `husky_sim` node runs in the robot's namespace (its
  parameters are the sim model); the controller is the node named in `BaseFollowerState.controller`, with all its
  parameters. Redo a report: `python3 -m husky_assembly_teleop.plugins.base_exp.report <run folder>`.
- Measurement (`tracking.py`): the monitor matches each new mocap pose to the path sent (`FollowerPath` geometry)
  and records position error (signed while driving, distance to the spot on a turn), heading error, along-track lag
  (timed), and the context: turning, curvature, progress, speed, phase. The follower's own errors are kept as
  diagnostics only. After the follower ends, recording goes on until the robot stood still for 0.5 s (1 cm, 1°),
  at most 3 s; the end error is taken there. ? Poses are timed by arrival until mocap is stamped.
- Experiments: an "Experiment" name in the panel; runs go to `data_experiment/base_exp/<name>/<date>_<time>_...`, the
  name is in experiment.json (`experiment_name`).
- Data location (2026-10-07): experiment data lives on the project's Google Drive folder, not in the repo. Its local
  path comes from `HUSKY_DRIVE_ROOT` or the monitor's `drive_root` parameter (`drive.py`), pointing at
  `2025-03 Husky Assembly` itself, since the path above it differs per user. No root, or no synced
  `data_experiment/base_exp`: `base_exp` setup fails and the analysis script exits. Folders under the root are never
  created locally (Drive would get a second folder of the same name). Analysis goes to the experiment's folder, `base_exp/<name>/_analysis`;
  the analysis skips folders starting with "_" (`_analysis`, `_archive`) and links runs by relative path. The old
  `data/recordings/` runs were moved to the Drive (`_archive/` for the old archive). Later: mocap_probe.
- Sim model (`husky_sim`): xICR, speed and steering efficiency, command delay, mocap delay (poses stamped with the
  time they describe), mocap noise (position, yaw); all in the setup key. `record.environment_label`: real, sim ideal
  (the model the controllers assume), sim model. Values for the model should come from the real robot.
- Plugin layout: `templates.py`, `plan.py` (Plan, plan_from), `auto.py`, `record.py` (setup, run folder),
  `report.py`, `markers.py` (3D view), `plugin.py` (panel, runs, automation, guard).
- Monitor:
  - `BaseInterface.send_path` and `stop_path`, and `BaseState.follower`.
  - Soft stop also stops the follower.
  - New signals in `world/signals.py`: `base_floor_pose` and `follower_*`.

- Automation (`plugins/base_exp/auto.py`):
  - **Start auto** draws from a grid (`auto.GRID`) at one speed (`auto.SPEED`, 0.2 m/s and 30°/s; every curve
    feasible at it, radius ≥ 0.5 m) and geometric only (`auto.MODE`; timed stays manual): equally spaced numbers per template,
    both directions. `Sampler` picks the template with the fewest successful runs in this collection run first, then
    its least covered cell, preferring the speed, mode and numbers used least (ties at random). A cell
    that fails the clearance check falls through to the next one (10 per template, 50 in all).
  - The path is checked in base_exp's own `PyBulletMirror` (`auto.Clearance`, whole robot, arms included) against
    other robots and every scene body, including the `obstacles` border walls. It must keep `PATH_CLEARANCE` = 0.3 m.
    Like every planner, base_exp owns its world; it shares only `world/mirrors`, not the base planner's code.
    Up to 50 samples are drawn; if none is clear, automation stops.
  - **Automation** (2026-10-07; entries renamed later): `Controller: standard paths` (default) drives `auto.STANDARD_SET`, 10 grid cells the same in every
    scenario (each segment type, mostly both directions), the least attempted first (`auto.StandardSet`; done and
    controller failures count). It resumes from the experiment's saved runs with the same `record.setup_key`
    (`record.earlier_runs`, read at series start), so every scenario gets the same attempts per path. Auto runs is
    then the total for the experiment, setup and automation (earlier attempts included): a Start runs only the rest. `Controller: random paths` is
    the `Sampler` above. `automation.paths` records which.
  - Automation needs the obstacles plugin's bodies in the scene, for the lab border.
  - It stops after N runs (0: until Stop). Controller failures (follower aborts off the path; "timed out: did not
    finish", which is stopped and still recorded through settling) are recorded and the series goes on. It pauses on
    problems around the controller (guard stop, mocap lost, bad path, silent or replaced follower, no answer); a
    pause shows an amber line in the panel and a warning in the log.
  - It drives back to the series' start pose (turn, drive, turn at 0.2 m/s and 30°/s; 0.2 m clearance; guarded;
    not recorded) only when no clear path is found where the robot stands; otherwise each run starts where the last
    ended. "Return every run" (off by default): before every run, unless within 5 cm and 5° of the start pose
    (`HOME_TOLERANCE`).
  - The guard (every run, manual or auto) checks the robot's live pose every tick against `STOP_DISTANCE` = 0.1 m.
    When it fires, it soft-stops the robot (`HuskyRobotInterface.soft_stop`), ends the run, and shows a red alert
    until the next Start. The operator switches the velocity controller back on and drives the robot clear.
  - `experiment.json` records `automation` (run, runs, samples, seed), `clearance`, `conditions` and `battery` at start.

## Comparison plan (2026-10-07)

- Fixed conditions, recorded with every run (`record.CONDITIONS`): stock Husky wheels (skid steer), arm stowed,
  RobotX hall tiles; plus the fixed speed and mode. The analysis keeps only runs that match and counts the rest.
- Questions, in order: (1) does the measured robot model explain the real errors (pure pursuit in sim ideal, sim
  model, real); (2) does a model-aware pure pursuit fix them (sim model for development, real for the result);
  (3) only if a gap remains: MPC with the better model against model-aware pure pursuit.
- First real data (5 manual runs): the robot turns about a point ~11 cm in front of the tracked point (xICR ≈ −0.11),
  ~250 ms from command to measured motion, speed efficiency 0.91, steering 0.98; an offline replay with these values
  reproduces the spot-turn drift, the crabbing on curves and the orbits at the end. Skid steer: the offset likely
  changes with load, floor and speed, hence the fixed conditions.

## Timing and identification

- Recordings carry `times`: each sample's mocap capture time and the stamp of the follower's latest command (robot
  clock, time synced). The live tracking uses capture times (`BaseState.last_fix_time`).
- `plugins/base_exp/identify.py` (experiment code; may move onto the robot later) fits the simulator's model to runs:
  delay, speed and steering efficiency, xICR. On the 5 real runs (tick clock): 250 ms, 0.92, 0.98, −11.9 cm. On a sim
  with 200 ms command delay, 50 ms mocap delay, 0.91/0.98, −11 cm (stamps): 180 ms, 0.91, 0.98, −10.9 cm.

## Model quality

- Recordings carry two message logs besides the tick-sampled signals: `commands`, every follower report (received,
  stamp, v, w, state code; 30 Hz), and `wheel_odometry`, the platform's `platform/odom` (28 Hz on Alice; received,
  stamp, v, w; empty in the simulator). From 1 s before the path was sent to the end of settling (`BaseInterface.follower_log`,
  `odometry_log`).
- The motion model is shared: `crl_husky/base_model.py` (`BaseModel`), stepped by `husky_sim` and by the replays.
- `plugins/base_exp/replay.py`: from start poses 0.2 s apart while following, the run's commands are fed through a
  model (zero-order hold, `delay`) for 0.25 to 2 s; the error is predicted against measured pose. Headline: 1 s ahead.
  `free_run` replays a whole run uncorrected, for plots.
- `identify.py` fits commands → motion, commands → wheels and wheels → motion (`SOURCES`). Commands are held until
  the next one (as on the robot and in the replay); wheel odometry, a measurement, is interpolated. Wheels → motion
  also tries negative delays. `cross_validated` scores each half of the runs with the model fitted on the other half.
- Synthetic check (`replay.synthetic`, robot_model.md "synthetic runs give their model back"): each run's commands drive the identified model;
  identifying those runs must give it back, replaying them no error. It caught a 20 ms delay bias when the
  identification interpolated commands while the replay held them.
- Check (sim, 200 ms command delay, 50 ms mocap delay, 0.91/0.98, −11 cm, full command log): identified 200 ms,
  0.91, 0.98, −11.0 cm; sim settings replay 0.0 cm median 1 s ahead, ideal 5.7 cm. Real (5 runs, tick clock): ideal
  3.3 cm, identified 1.4 cm median 1 s ahead.

## Model-aware pure pursuit

- Robot models: `crl_husky/config/base_models/<name>.yaml` (xICR, speed_efficiency, steering_efficiency,
  cmd_delay_sec; `base_model.load_model`). `ideal` and `alice_tiles` (from real_1007: −0.129, 0.88, 1.01, 0.22 s).
- Set independently: follower param `model` (sim launch `controller_model:=`, robot launch `model:=`); simulator
  param `model` (sim launch `sim_model:=`, single values still override). Both recorded with every run; the analysis
  labels the controller "PP <model>" unless ideal, and names the sim model in the Setups table.
- Pure pursuit with a model (`pure_pursuit.py`): steers the turning centre (`ahead` = −x_icr in front of the tracked
  point), which moves like the ideal differential drive; predicts its pose to when the new command acts (commands
  sent in the last delay, `PREDICTION_STEP` 10 ms); divides commands by the efficiencies. `make_path` shifts the
  path; a turn on the spot becomes turn – short straight drive (forwards or backwards) – turn, so the tracked point
  ends on the pose. During a spot turn the tracked point still swings (skid steer cannot turn about it).
  ! Timed paths are rejected ("bad path") when x_icr ≠ 0.
- Check in the sim (alice_tiles robot, 8 auto runs each, experiment model_aware_check): plain PP 2 controller
  failures (orbits), end 8.7 cm; PP alice_tiles 0 failures, end 1.3 cm. Moving error stays dominated by spot turns
  (15–17 cm at the tracked point, by physics).
- Next: tuned PP vs plain PP in the alice_tiles sim, then on Alice.

## Analysis

`scripts/analyze_base_exp.py --experiment <name>` (venv and ROS sourced) loads the runs once and writes up to three
reports to `data_experiment/base_exp/<name>/_analysis/` on the Drive. Code in `plugins/base_exp/analysis/` (pandas,
never imported by the plugin): `common.py` (loading, labels, Markdown tables), `controller.py`, `robot_model.py`,
`commands.py`. Every run is a path run (standard or random paths) or a constant-command run (`common.PATHS`,
`COMMANDS`); `Experiment.only(kind)` gives a report its runs. A sim run without a model name takes the name another
run gave the same values; two value sets under one name are numbered like scenarios ("sim m", "sim m #2"). A robot is the part of a scenario before the ·; constant-command runs are "<robot> · constant commands"; robot_model.md lists each robot's scenarios under their summary.md names. Left out (counted in "left out", folders kept): runs with outcome "e-stopped" (the
plugin ends a run as soon as `BaseState.estopped` is set, and automation pauses), and runs listed in the experiment
folder's `_excluded.txt` (`common.EXCLUDED`; one folder name per line, `# reason`).

Terms, the same in the panel, the reports and the manual: Automation "Controller: standard paths", "Controller:
random paths", "Robot: constant commands"; a path run, a constant-command run; the path grid, the command grid and
their cells; a round (every standard path, or every command cell, once); attempts.

- `summary.md` opens with what it shows, with numbers and sections: how well each controller follows the paths,
  whether the adapted model helps, whether the simulator predicts the real result, where the errors come from. Then
  1 scenarios, 2 overview (no bold), 3 comparisons: `by_robot` (each robot's controllers on the paths they all
  finished, bold within the robot, "(not collected)" rows for missing controllers) and `sim_vs_real` (per
  controller, no bold); mean of path means ± the standard deviation between repeats of one path, pooled. 4 where
  the errors come from (robot, then segment or template, controllers stacked, bold within them), 5 failures and
  worst runs, 6 plots without the ideal simulator. Bold only where rows are compared directly (`markdown` `within`).
  The controllers, from the path runs. Scenarios "<robot> · <controller>" (e.g. "sim alice_tiles · PP ideal"; unnamed sim
  models "sim model A"; distinct setups sharing a label get "#2"). Headline on the standard paths: per scenario
  attempts, success, and errors over the standard paths every scenario finished, each once per scenario; without
  standard-path runs, over every path. A per-path table (done/attempts · end · moving cm per scenario). Every path
  run (random paths too) by segment type and template; failures with progress reached and largest error; the worst runs
  by end position; plots. Best value bold, except where every row ties.
- `robot_model.md` opens with what it shows, each with its numbers and section: (1) the real robot's model and
  whether one model fits all its runs, flagging values whose per-template fits differ by more than `TOLERANCE`;
  (2) it predicts better than the ideal model but not perfectly; (3) the checks. Then 1 scenarios (robot, scenario,
  runs, how the robot moves, what the controller assumes, what for), 2 the model, 3 stability (each run fitted on
  its own: median, spread = sd, n; first and second half; per template; `model_stability.png`; the simulator's spread
  is the method's noise), 4 prediction, 5 checks, 6 details. From every run: grouped by robot (real, sim ideal, sim <model>), path runs with
  every controller and constant-command runs pooled. A Runs table
  with what each kind is for and the kinds missing (real; sim ideal; sim running the model identified on the real
  robot, matched within `TOLERANCE`). Identified response (commands → motion) with the sim's set values beside it;
  the real robot through the wheels; the model as crl_husky yaml and launch line; replay prediction 1 s ahead (ideal,
  identified cross-validated, sim settings) overall and by segment; checks (a sim runs the real model; identification
  gives the sim's model back; the sim's model predicts its runs; synthetic runs give their model back).
- `constant_commands.md` (`analysis/commands.py`), only with constant-command runs. Per run: steady means from 1.2 s after the step to the stop (forward, sideways from mocap
  gradients; turn rate from a line fit to yaw), so speed/steering efficiency and xICR; delay where that line (or the
  distance along the start heading, on a straight) extended back meets the start: exact for a pure delay, + τ for a
  lag, + half the ramp for an acceleration limit; from the wheel odometry the steady wheel speeds, delay to 10 % and
  rise 10–90 %. Per cell mean ± sd; per value the spread across cells against within cells and a plane fit
  a + b·|v| + c·|ω|; left − right and reverse − forward; wheel gains; heatmaps, trends, step plots.

Results summary: the analysis also writes `results_prompt.md` (`controller.RESULTS_PROMPT`, with the folder filled
in). Hand it to a subagent as is; it writes `results.md` with fixed sections (Headline, Where the errors come from,
Failures and outliers, Caveats, Next steps), so every collection is summarised the same way.

## Constant commands (2026-10-07)

Does the model change with speed and turn rate? Constant commands, open loop, on the command grid (`plugins/base_exp/twist.py`;
"Automation: Robot: constant commands").

- Cells: v 0, 0.1, 0.2, 0.3 m/s × ω ±0.15, 0.3, 0.5, 0.8 rad/s; straights at 0.1–0.3; reverse −0.2 with ±0.3, 0.8;
  cells beyond 0.5 m/s at a wheel left out (37). `TwistGrid` hands them out least attempted first, ties at random,
  resumed from the experiment's runs with the same setup (`record.earlier_runs`), like the standard paths.
- A constant-command run (`plugin._run_twist`): 0.5 s of zero commands, the command for 4 s (`twist.SEGMENT`), stop, settle. Sent
  every tick with `BaseInterface.send_twist` (`require_controller=False` in the simulator, which has no velocity
  controller, and for stops). Recorded like a run: its settings as "template" (name "Twist"), `twist_plan` (the
  ideal model's arc) as the path, the command under the follower command's signal name and in the `commands` log, so
  reports and replays read it unchanged; `command_source: monitor` in experiment.json.
- Drives back only when more than 0.75 m from the start; a drive back that times out within 0.3 m of it counts
  (pure pursuit circles the goal on a robot with xICR), for every automation.
- Check in the simulator (alice_tiles: −12.9 cm, 0.88, 1.01, 220 ms; 13 runs): every cell 0.88 / 1.01 /
  −12.7 to −13.2 cm, delay 201–219 ms. The ±2 mm in xICR is the simulator's Euler step (heading at the step's
  start: −v·dt/2), not the analysis.

## Run in the simulator

In its own ROS domain (`ROS_DOMAIN_ID=70`), never on the fleet's domain 80 or on a robot: the simulator
obeys the same cmd_vel as the real base.

```bash
# mocap_relay:=true: a second relay brings the real lab's mocap into this domain, without the simulated robot (1840)
ros2 launch crl_husky pure_pursuit_sim.launch.py namespace:=a200_0804 mocap_id:=1840 mocap_relay:=true
# list the other robots too, so they appear (from the relay) and are avoided
ros2 run husky_assembly_teleop husky_monitor --ros-args -p robots:="['alice','belle','cindy']" \
  -p plugins:="['base_exp','obstacles']" -p viser_port:=8095
```

On a robot: `ros2 launch crl_husky pure_pursuit.launch.py`, with the platform velocity controller active.
